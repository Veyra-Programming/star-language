## 1. Vision & Architecture

The Star Android Native Backend provides native Android execution for Star mobile applications using the high-performance StarVM bytecode engine, a C++20 JNI native bridge, hardware-accelerated SurfaceView rendering, official Gradle 8.2 wrapper scaffolding, and direct Android system service integrations.

```text
                  🌟 Star Source Code (.star)
                              │
                    AST → Star IR Compiler
                              │
                  Star Bytecode (.starb / IR)
                              │
                  📦 .starmobile Bundle
                              │
              ┌───────────────┴───────────────┐
              │     Android Builder           │
              │  (Gradle Project Generator)   │
              └───────────────┬───────────────┘
                              │
             ┌────────────────┴────────────────┐
             ↓                                 ↓
   ┌────────────────────┐            ┌────────────────────┐
   │  Android JVM Host  │ ◄── JNI ──►│  Star Native NDK   │
   │  (StarActivity)    │            │ (StarVM / Runtime) │
   ├────────────────────┤            ├────────────────────┤
   │ StarSurfaceView    │            │ Layout Engine      │
   │ InputBridge        │            │ Gesture Recognizer │
   │ AndroidDeviceBridge│            │ Command Stream Gen │
   └─────────┬──────────┘            └─────────┬──────────┘
             ↓                                 ↓
     🤖 Android APK / AAB Distribution Package
```

## 2. JNI / NDK Native Interface

The Android runtime communicates with StarVM through high-speed JNI native interfaces defined in `StarNativeBridge`:

```java
package org.starlang.runtime;

public class StarNativeBridge {
    static {
        System.loadLibrary("starnative");
    }

    public native boolean initRuntime(String appName, int width, int height, float density);
    public native boolean loadBytecode(byte[] bytecode);
    public native void dispatchTouchEvent(int phase, int pointerId, float x, float y);
    public native byte[] renderFrame();
    public native void dispatchLifecycle(String state);
    public native boolean dispatchBackPress();
}
```

## 3. Android Activity Lifecycle Mapping

Host OS Activity callbacks are mapped directly into Star lifecycle state transitions:

| Android Activity Callback | Star Lifecycle State | Action |
| :--- | :--- | :--- |
| `onCreate()` | `Mounted` | Viewport initialized, JNI runtime bound. |
| `onResume()` | `Resumed` | Rendering loop active, touch inputs accepted. `Mobile.on_resume()` executed. |
| `onPause()` | `Paused` | Rendering paused, battery consumption throttled. `Mobile.on_pause()` executed. |
| `onDestroy()` | `Detached` | Resources released, VM teardown. |
| `onBackPressed()` | Event Dispatch | `Mobile.on_back_press()` executed. Return `true` to cancel default OS exit. |
| `onLowMemory()` | Warning Hook | `Mobile.on_memory_warning()` executed to purge cached assets. |

---

## 4. Input & MotionEvent Bridge

Android `MotionEvent` actions are converted into normalized Star touch streams:

| Android MotionEvent Action | Star TouchPhase | Recognition Result |
| :--- | :--- | :--- |
| `ACTION_DOWN` / `ACTION_POINTER_DOWN` | `TouchStart` | Contact initiated, touch point registered. |
| `ACTION_MOVE` | `TouchMove` | Coordinates tracked for `Pan`, `Pinch`, `Rotate`. |
| `ACTION_UP` / `ACTION_POINTER_UP` | `TouchEnd` | Contact released, evaluated for `Tap`, `DoubleTap`, `LongPress`, `Swipe`. |
| `ACTION_CANCEL` | `TouchCancel` | Active touch sequence cleared. |

---

## 5. Android System Services Bridge

Star Mobile APIs seamlessly map to native Android framework services:

- **Haptics/Vibration**: Maps to `android.os.Vibrator` and `android.os.VibrationEffect`.
- **Storage**: Backed by `androidx.security.crypto.EncryptedSharedPreferences`.
- **Battery**: Queries `android.os.BatteryManager`.
- **Clipboard**: Reads/writes `android.content.ClipboardManager`.

## 6. Android SDK Integration & Gradle Project Structure

Full Android builds in Star integrate with and utilize the local **Android SDK** (`ANDROID_HOME`, `ANDROID_SDK_ROOT`, or default system SDK paths). The toolchain discovers installed platforms (`android-34`), build-tools, and platform-tools (`adb`).

When compiling, Star automatically configures `local.properties` with the detected `sdk.dir`:

```properties
## Auto-generated by Star Language Android Toolchain
sdk.dir=C\:/Users/<User>/AppData/Local/Android/sdk
```

The `AndroidProjectGenerator` produces a standalone, reproducible Gradle project bound to the Android SDK:

```text
build/android/project/
├── local.properties          # Configured with sdk.dir for local Android SDK
├── gradle.properties         # AndroidX & JVM optimization flags
├── build.gradle              # Android Gradle Plugin 8.2.0
├── settings.gradle
└── app/
    ├── build.gradle          # compileSdk 34, targetSdk 34, C++20 NDK
    └── src/main/
        ├── AndroidManifest.xml
        ├── assets/
        │   └── app.starmobile
        ├── cpp/
        │   ├── CMakeLists.txt
        │   └── star_jni_bridge.cpp
        └── java/
            ├── <package>/
            │   └── MainActivity.java
            └── org/starlang/runtime/
                ├── StarNativeBridge.java
                └── StarSurfaceView.java
```

## 7. Keystore & Signing Management

Star provides a zero-friction development experience with rigorous security for production releases:

### 7.1 Automatic Development Keystore
On first build, Star automatically provisions a development keystore at:
```text
~/.star/android/debug.keystore
```
All debug APKs and AABs are automatically signed with standard development credentials (alias: `androiddebugkey`, password: `android`).

### 7.2 Release Signing Configuration
For production release builds (`--release`), Star requires explicit developer key configuration in `star.toml` rather than silently generating unknown keys:

```toml
[android.signing]
keystore = "keys/release.keystore"
alias = "star_production_key"
store_password = "ENV:STAR_KEYSTORE_PASS"
key_password = "ENV:STAR_KEY_PASS"
```

Or via environment variables:
```bash
export STAR_ANDROID_KEYSTORE="keys/release.keystore"
export STAR_ANDROID_KEY_ALIAS="star_production_key"
export STAR_ANDROID_KEYSTORE_PASSWORD="password"
```

## 8. CLI Commands & Artifact Targets

```bash
# Build Development APK (Auto-signed with debug keystore)
star build apk [entry.star]

# Build Production Release APK (Requires configured release key)
star build apk --release [entry.star]

# Build Android App Bundle (.aab) for Google Play Store
star build aab [--release] [entry.star]

# Build Complete Android Distribution Suite (Both APK and AAB)
star build android [--release] [entry.star]

# Execute on connected device, emulator, or simulated host
star run android [entry.star | app.apk | app.starmobile]
```

### 8.1 Smart Entrypoint Resolution
When commands like `star build android`, `star build apk`, or `star run android` are called without an explicit file path, Star automatically resolves the entrypoint with zero configuration using the following priority:
1. Explicit CLI argument (with automatic `.star` suffix extension).
2. Project configuration in `star.toml` (`entry` field).
3. Conventional standard entry files: `main.star`, `app.star`, `src/main.star`, `src/app.star`.
4. Solitary `.star` file in the current working directory.
5. Flagship repository showcases (e.g. `examples/ui_motion_showcase.star`).
If no candidate is found, a clear and actionable diagnostic is printed instead of an unhandled traceback.

### 8.2 Gradle Wrapper & ProGuard/R8 Integration
Every generated Android project in `build/android/project` is fully self-contained and pre-configured with:
- `gradle/wrapper/gradle-wrapper.properties` (Gradle 8.2 Distribution).
- `gradlew.bat` (Windows) & `gradlew` (POSIX / macOS / Linux).
- `app/proguard-rules.pro` with keep-rules for `org.starlang.runtime.**` JNI native boundaries.
- Android SDK `local.properties` (Targeting API 34 / Android 14+ Google Play compliance).
Projects can be opened directly in Android Studio or compiled via `./gradlew assembleDebug` out of the box.

## 9. Star Go — Expo Go Companion Architecture & QR Code Live Testing

Star includes a complete, dedicated Android companion application (`org.starlang.go`) located in the root `android/` directory and `apps/star_go/`, modeled after the industry-standard **Expo Go** developer workflow.

### 9.2 Developer Workflow (`star go` & QR Scanning)
1. **Start the Dev Server**:
   ```bash
   star go [file.star] [--port 8088]
   ```
   This automatically detects your LAN IP (e.g. `192.168.1.15`), bundles the application into `.starmobile`, and renders a scannable **ANSI Terminal QR Code** (`star://<ip>:8088`).
2. **Scan & Test on Physical Device**:
   Open **Star Go** on your Android phone, tap **"Scan QR Code"**, and point the camera at your terminal screen. The app downloads the bundle over WiFi, runs on native SurfaceView, and connects to the Fast Refresh event stream.
3. **Fast Refresh & Hot-Reloading**:
   Any edits saved to the `.star` source file trigger an instant sub-20ms re-bundle and broadcast reload event to all connected devices without rebuilding or re-installing APKs.
4. **Developer Options Menu**:
   Shake your Android phone at any time (or press `m` in the terminal) to bring up the floating Dev Menu: Fast Refresh toggle, Manual Reload, Performance HUD (60 FPS), or Disconnect.
